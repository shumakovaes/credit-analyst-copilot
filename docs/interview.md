# Резюме и собеседование

## Два пункта для резюме

- Разработал учебного помощника кредитного аналитика на Python, LangGraph, FastAPI и PostgreSQL: формирование SQL-плана, проверка AST и прав доступа, ограниченное исполнение, исправление ошибок, журнал, таблицы и графики. Подготовил отдельную синтетическую базу и адаптер к сервису кредитной аналитики.
- Реализовал подключения к LLM API с JSON Schema, тесты SQL-политики и read-only роли, набор из 20 вопросов с эталонными запросами. Проверил 58 автоматических тестов и сквозной деморежим; живую оценку LLM предусмотрел отдельной командой.

Формулировки рассчитаны на самостоятельный разбор и воспроизведение проекта. Пока live-прогон не выполнен, не указывайте выдуманную точность LLM, скорость работы модели или внедрение в банке.

## Вопросы, на которые нужно уметь ответить

**Почему здесь агент, а не один вызов модели?** План попадает в граф, где результат проверки меняет следующий шаг. Агент может запросить уточнение, исправить SQL после ошибки, прекратить опасный запрос или выполнить его. Число итераций ограничено.

**Почему нельзя проверить SQL регулярным выражением SELECT?** Запись может быть внутри WITH, SELECT может вызывать функции с побочными эффектами, несколько выражений можно соединить. Проверяются AST, области видимости, источники и функции, а не первое слово.

**Зачем read-only транзакция, если есть reader-роль?** Это разные ограничения. Роль запрещает запись в таблицы, транзакция дополнительно ограничивает операции, а AST запрещает нежелательные функции и источники. Ни один из этих механизмов по отдельности не решает всю задачу.

**Как отличить безопасный запрос от правильного?** Безопасность касается допустимых действий и ресурсов. Правильность — соответствия бизнес-вопросу. SELECT может быть безопасным, но неверно считать долю плохих кредитов или смешивать даты. Поэтому есть словарь и eval-набор.

**Зачем просить уточнение про риск?** В базе нет истории снимков риска, и слово «риск» может означать score, долю B, текущую просрочку или результат правил. Подмена одного другим создаёт правдоподобный неправильный ответ.

**Почему данные результата не отправляются обратно в LLM?** Для этого объёма задачи достаточно детерминированного ответа и графика. Это снижает передачу данных провайдеру и исключает добавление неподтверждённых чисел при пересказе. Но неверный SQL всё ещё может дать неверный бизнес-ответ.

**Что доказывают 12/12?** Только работоспособность фиксированного демонабора и инфраструктуры. Генерация SQL моделью этим не измеряется.

**Как проверяется исправление ошибки?** Есть сценарий неизвестного столбца, который исправляется до выполнения, и интеграционный тест настоящей PostgreSQL-ошибки группировки. Отдельно проверяется завершение после третьей неудачной попытки.

**Почему журнал в SQLite, а данные в PostgreSQL?** Аналитическое соединение остаётся с правами только на чтение. Локальный журнал имеет собственный ограниченный способ записи и не принимает SQL от модели.

**Как подключён первый проект?** Через отдельные представления с фиксированным контрактом. Первый сервис не зависит от Copilot, а Copilot может работать на собственной демобазе.

**Что нужно для реальной команды банка?** Аутентификация и права на уровне строк, политика передачи данных модели, хранение и аудит журналов, мониторинг и контроль расходов, независимая проверка безопасности, реальные данные и более широкий отложенный eval-набор.
