# Политика SQL и границы защиты

Цель — ограничить последствия неверного или навязанного модели SQL. Инструкции в промпте не считаются достаточной защитой. Модель не получает административные реквизиты, а её SQL проходит независимый код проверки.

## Проверки перед выполнением

1. Не более 8 000 символов, ровно одно выражение SELECT/UNION; нерекурсивные CTE допустимы.
2. Явный разрешающий список AST-конструкций. DML, DDL, COPY, INTO, блокировки, транзакционные команды, рекурсия, табличные функции и неизвестные конструкции отклоняются.
3. Только физические таблицы/представления `copilot_data` из каталога. CTE разрешаются с учётом областей видимости. Системные каталоги и исходные `clean`/`raw` не разрешены.
4. Проверка столбцов и псевдонимов по фиксированной схеме. SELECT * запрещён, COUNT(*) допустим.
5. Явный список агрегатных/аналитических функций. Файловые, сетевые, административные, advisory-lock функции и pg_sleep запрещены. Пользовательские функции и квалифицированные вызовы функций не поддерживаются.
6. До трёх JOIN с ON/USING, без CROSS JOIN. Это уменьшает поверхность тяжёлых запросов, но ON TRUE сам по себе не исключается: дополнительные ограничения действуют ниже.
7. LIMIT/OFFSET только числовые, не более 10 000. Внешний LIMIT уменьшается до `max_rows + 1`; лишняя строка служит для обнаружения усечения. Маленький пользовательский LIMIT сохраняется.
8. Выполняется SQL, заново сгенерированный из проверенного AST. В исполнитель не передаётся непроверенный текст модели.

Отсутствующий столбец и некоторые синтаксические ошибки допускают исправление. Попытка доступа к чужой таблице или запрещённая конструкция прекращают обработку без повторного запроса к модели. Исправление никогда не меняет политику доступа.

## PostgreSQL

Reader-роль не владеет аналитическими объектами, имеет USAGE схемы и SELECT. API проверяет отсутствие административных флагов, права CREATE в `copilot_data` и прав изменения разрешённых объектов. Настройка роли `default_transaction_read_only=on` включена дополнительно.

Каждое выполнение явно начинается с READ ONLY. Устанавливаются `statement_timeout=1500ms`, `lock_timeout=500ms`, `search_path=pg_catalog`. Таблицы в SQL указываются с именем схемы. EXPLAIN без ANALYZE проверяет оценку стоимости; слишком дорогой план отклоняется. Результат ограничен 200 строками и 200 000 байтами.

Read-only настройку сессии пользователь PostgreSQL обычно может переключить. Поэтому в тесте она намеренно выключена, после чего DELETE всё равно отклонён из-за отсутствия прав. И наоборот, одних прав SELECT недостаточно против всех побочных эффектов функций: поэтому нужен разрешающий список AST/функций.

Reader может иметь стандартный доступ PostgreSQL к части системных каталогов и TEMP через PUBLIC. Приложение не использует эти возможности: обращения к ним запрещены на уровне SQL-политики. Это не утверждение, что роль изолирована от всех метаданных PostgreSQL вне данного приложения.

## LLM, данные и ошибки

Модель получает вопрос и описание схемы. Данные строк не отправляются ни для пересказа, ни для контекста следующих сообщений. Сам вопрос пользователя может содержать данные — его отправка провайдеру является частью live-режима.

Ответ проверяется Pydantic-схемой. Неполный JSON, отказ провайдера, HTTP-ошибка или timeout не приводят к выполнению SQL. Ключи и тела ошибок провайдера не записываются в пользовательский журнал. HTTP redirect автоматически не разрешается. Для внешних endpoint требуется HTTPS; HTTP допускается только для локального адреса.

На один вопрос максимум три попытки. Таймаут LLM HTTP-клиента по умолчанию 20 секунд относится к операциям ввода-вывода, а не к строгому общему wall-clock deadline. API принимает максимум два одновременных вопроса. Локальные ограничения не заменяют контроль расходов провайдера и защиту публичного сервиса.

## Остаточные риски

- Безопасный SQL может неверно отвечать на бизнес-вопрос. Это проверяется сравнением с эталонами и человеком, не AST.
- EXPLAIN даёт оценку стоимости, а не точное время; таймаут — отдельная граница.
- SQLGlot и PostgreSQL — разные парсеры; используется узкое подмножество и пересборка SQL, но формального доказательства эквивалентности нет.
- Администратор схемы/БД и настроенный LLM endpoint считаются доверенными. Изменение представлений администратором меняет разрешённые данные.
- Журнал содержит вопросы, SQL и результаты. Он хранится локально, без шифрования и автоматического удаления. Для настоящих банковских данных потребуются политика хранения, контроль доступа и аудит.
- Приложение рассчитано на одного локального пользователя. UUID диалога не является механизмом авторизации; API нельзя выставлять в интернет без отдельной защиты.

Эта политика проверена тестами, но не проходила независимый аудит безопасности и не объявляется готовой защитой банковского продакшена.
